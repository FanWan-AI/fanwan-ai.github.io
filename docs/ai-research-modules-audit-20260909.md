# AI 论文中心与 AI 模型雷达：升级前审查

审查日期：2026-09-09。范围：产品体验、公开数据、前端消费逻辑、内容生成与发布流程。本轮不修改生产代码、不重跑付费生成任务、不提交或推送。

## 结论

两个模块的基础结构值得保留，但当前更像信息聚合器，而不是研究判断与技术选型工具。论文中心的问题优先级更高：生成失败后的原始信息流被当成正式精选发布；模型雷达已有摘要库，但“今日灵感”允许未加工的高热度模型占据首页。只补翻译、补一段文字或更换配色，不能解决核心问题。

目标建议：论文中心回答“这篇研究改变了什么、哪些方法值得借鉴”；模型雷达回答“我的任务可以用什么、需要什么条件、怎么试”。与 AI 创业观察的商业判断分工，避免三处重复搬运新闻。

## 审查方式与边界

- 产品审查按入口、判断内容、进入原始资料的路径组织；用户本轮提供的三张截图作为明确的视觉证据，原样复制并逐张检查。
- 直接获取线上 JSON，抽查论文最近三期、领域脉络索引与 Agent 样例、模型当期发布及历史摘要库。
- 读取本地对应代码和 GitHub Actions 实际运行日志，区分代码路径、线上事实、推断和建议。
- 实时浏览器多次连接或截图超时，未得到可接受的新交互截图；因此本报告不是完整交互验收，不将该工具故障归因于网站。手机端、键盘操作、屏幕阅读器和精确对比度仍需后续实测。
- 364 条模型记录“有中文摘要”不等于摘要的技术结论已经逐条核实；本轮未复现实验、逐条验证外部论文或模型能力。

来源：[当期公开数据](https://fanwan-ai.github.io/data/ai/scholarpush/index.json)、[9 月 7 日](https://fanwan-ai.github.io/data/ai/scholarpush/2026-09-07.json)、[9 月 5 日](https://fanwan-ai.github.io/data/ai/scholarpush/2026-09-05.json)。这些是页面发布了什么的证据，不为其中新闻或社区说法背书。

### 优点

- 今日精选与长期演进分开，适合“每天发现、逐步积累”的使用习惯。
- 日期归档、检索、标签、论文及代码链接已有基础，不必重建全部交互。
- 统一站点视觉具有辨识度，问题不在于缺少装饰。

### 问题与根因

1. **内容准入失效。** 来源池将学术源与社区、教程混合。`_fallback_scholarpush` 按时间取前 8 条，不保证是论文、不保留必要的质量门槛；非 arXiv 默认记为 blog，无法覆盖真实学术来源的多样性。
2. **中文字段被英文填充。** 不只是前端选错语言。线上 `title_i18n.zh`、`summary_i18n.zh` 本身就是英文。降级路径直接把 headline 写入 zh；摘要选择没有可靠的语种检查，还存在按字符长度择优的问题。
3. **固定分数制造了不应有的确定性。** 50 和 30 是降级函数写死的默认值，不是这些条目的独立评估。页面又把它们汇总成平均影响评分，放大了误导。
4. **任务成功不等于内容合格。** [9 月 9 日运行 34293570207](https://github.com/FanWan-AI/fanwan-ai.github.io/actions/runs/34293570207) 整体 success，但日志明确记录所有提供方失败、采用 fallback，随后仍写入并发布 JSON。最后记录的提供方错误是 Aliyun access_denied / HTTP 403，不能据此断言 DeepSeek 同样返回 403，更不能直接判断 DeepSeek 模型能力差。
5. **不是当天完全抓不到论文。** 同一运行日志记录 arXiv API fallback 得到 84 条；后续时间窗口、提示词候选和排序仍会改变入选集合。因此需要分别审查采集覆盖和选取规则，不能只加 RSS。

代码定位：`tools/scholarpush/ai_blog_pipeline.py:1981`（降级选取、固定分数）、`:2586`（失败后继续生成公开数据）、`:895`（中文摘要择取）、`:2821`（主流程）；`lab/ai-paperhub.html:698`（语言字段回退）、`:847`（分数汇总）。

## 2. 论文卡片：阅读与借鉴（状态：缺少可用的研究解读）

![用户提供的论文卡片截图](D:/Code/fanwan-ai.github.io/.tmp/audit-research-20260909/02-paper-cards.png)

- **断句并非单纯 CSS 截断。** 线上第一条 summary 在 280 个字符处以半个单词结束，数据到前端时已经损失内容。候选加工代码默认 `summary[:280]`，fallback 复用了这一段；教程 RSS 原本也可能只有摘要。前端加展开按钮不能恢复不存在的文字。
- **没有回答研究者的问题。** 当前主要展示标题、摘要、分数、标签、外链；没有呈现方法相对前作的变化、实验条件、适用边界和可复用动作。代码虽曾设计 reusability / limitations，当前数据全空，卡片模板也没有把它们作为主要信息展示。
- **首屏资源分配不合理。** 搜索、历史标签和四张统计卡占据主要视线，读者要往下找才看到研究内容。低信息量被大留白和装饰放大。
- **分类与来源混杂。** `WWW.REDDIT.COM` 被当作主题标签；中文、英文技术标签并存；标签计数从全历史计算，而旁边统计是当日，作用范围不够清楚。
- **链接语义不准确。** 社区帖和教程按钮都被称作“项目”，还可出现重复箭头；应区分论文、代码、作者页面与讨论。
- **加载结构有规模风险。** 线上日期索引有 325 个日期，初始化会对全部日期发起读取并等待 `Promise.all`，才完成精选与脉络的主要渲染。此处是代码确认的性能风险，不是本轮测出的 325 次实际网络时延。

代码定位：`tools/scholarpush/ai_blog_pipeline.py:405`；`lab/ai-paperhub.html:760`、`:912`、`:1413`、`:1474`、`:1856`。

## 4. 模型雷达：今日灵感与技术选取（状态：首页发布质量不足，历史库可复用）

![用户提供的模型卡片截图](D:/Code/fanwan-ai.github.io/.tmp/audit-research-20260909/03-model-cards.png)

### 优点

- GitHub 工程与 Hugging Face 模型分开，方向合理，避免把工程框架和模型权重混为一谈。
- 已有按任务浏览、排序、历史归档、摘要缓存、分阶段生成和发布审计。
- 线上 Hugging Face 历史库有 364 条标为 qualified 的记录，均有包含中文的摘要字段；当天 GitHub 的 1 条公开卡片也有中文摘要。因此不能说整个摘要系统已经失效。

### 缺失介绍的直接原因

9 月 9 日 Hugging Face 的 8 条公开项全部为 passonce，全部没有任何语言的摘要，且标有 needs_tri / fast_first / placeholder。前端逻辑是“摘要为空就不生成段落”，所以截图中的空白卡片与数据完全一致。

`data_analysis.mjs:152` 明确允许 Hugging Face 高热度项绕过摘要长度要求：默认 likes 至少 500 **或** downloads 至少 200000 即可通过快速路径；`:160` 还允许 fast_first。发布阶段又接受这些 passonce 记录。不能只让前端显示“暂无介绍”就认为问题解决。

发布审计显示输入有 25 条 passonce、1 条 qualified，输出为 8 条 passonce、0 条 qualified。发布逻辑先去掉历史库中已存在的项目，再去掉热榜重复，强调“不重复出现”却没有保证留下的内容可读。既有模型的重大升级也可能因 canonical id 不变而被排除，应改成对事件和版本去重。

来源：[当期模型数据](https://fanwan-ai.github.io/data/ai/modelswatch/daily_hf.json)、[历史摘要库](https://fanwan-ai.github.io/data/ai/modelswatch/corpus.hf.json)、`tools/modelswatch/audit/2026-09-09_publish_audit.json`、`tools/modelswatch/qualify_publish.mjs:1502`、`lab/modelswatch.html:1545` 与 `:1598`。

### 产品层面的不足

- 下载、likes、stars 表示关注或使用信号，不等于适合读者的任务，更不等于经过本站评测。
- 不同任务模型、第三方打包和同家族量化版本混排；读者看不到为什么选它、原版是谁、自己应该选哪个版本。
- 缺少最低限度的任务说明、适用/不适用情境、运行方式及验证入口；许可证和运行条件在需要决定采用时必须可查，不必恢复成满屏小标签。
- “访问”把判断成本全部交回外部网站。应提供明确的下一步，例如读模型卡、看示例、对照同类，而不是替读者猜能力。
- 截图中内容最稀缺，装饰与指标反而最突出。应让一句中文用途和推荐理由成为主角，热度退为次级信息。

## 共同风险与升级顺序

### 首先修发布可信度，而不是先换模型或框架

1. 生成失败、语种不符、摘要为空、来源类型不符，不进入正式精选；保留上一有效版本和真实日期，并向维护者报告原因。
2. 固定默认分数不上站；未评价应明确为空。论文“有代码”与“已复现”分开，模型“官方报告”与“本站实测”分开。
3. 获取原始材料后再解读。论文至少要有完整摘要和可信论文身份，选中深读项再处理全文、表格；模型使用模型卡、README、版本说明及许可信息。原始来源、出处定位和内容哈希应可追溯。
4. 以内容版本或发布事件为去重单位；建立日报与历史库的正确关系，而不是只许陌生名字进入日报。
5. 日志区分抓取、生成、验证、发布状态；“Actions success”不能替代内容验收。

### 保持少量入口，增强每条信息的用处

| 模块 | 保留的结构 | 应补齐的核心内容 | 应减弱或移除 |
| --- | --- | --- | --- |
| 论文中心 | 今日精选 + 演进轨迹 | 研究问题、相对前作的变化、关键证据与实验条件、局限、可借鉴动作 | 社交新闻混入、默认分数、大面积无助判断的统计 |
| 模型雷达 | 今日灵感 + GitHub/HF 分类库 | 中文用途、此次变化、适用边界、运行/许可条件、官方试用入口、同家族版本关系 | 无摘要卡片、把热度当能力、重复量化包挤占精选 |

建议初版每日仅精选 3–5 项，每项先用一屏内的短解读帮助判断，再按需展开证据。此数字是建议上限，不是凑满的配额；是否真正有用由试读决定。不要再增加一排新的子模块。

### 技术与维护成本

- 先规则过滤和去重，再对少量候选阅读/生成；缓存按内容哈希失效，中文优先，其他语言分阶段补齐。避免每次对全历史做全文翻译。
- 先加载当期数据；历史搜索使用预生成索引或按需加载，不让全部归档阻塞首页。
- 两页大量逻辑内联，后续应拆出共享数据契约、取数、筛选和渲染测试；不必为了此次升级先引入新前端框架。
- 论文卡片部分外部/生成文本直接拼入 innerHTML，需补文本转义及链接协议校验。本轮只定位代码风险，未做攻击验证。
- 当前两个工作流都按每月奇数日运行：论文计划 UTC+8 08:00，模型计划 10:30；并非真正每天，月界也不保证严格相隔 48 小时。升级时应统一名称、显示日期与实际发布节奏。
- 若“全面覆盖所有 AI 子领域”与“少噪声且低维护成本”同时要求，必须取舍；建议领域广度留给分类库，首页只呈现少量值得判断的变化。

## 建议验收标准（尚未实施）

- 正式精选不含无关社区帖子、空摘要或伪装成中文的英文；原始论文标题可保留英文作核对。
- 每条有可定位来源，重要数字带实验/统计口径；无证据的能力、许可证和显存条件不猜填。
- 任意一个外部接口或 LLM 失败，不覆盖上一有效版本，不把旧内容改日期冒充新一期。
- 论文读者能说出“学到了什么、适合借鉴哪里”；模型读者能说出“能做什么、适不适合我、如何验证”。先人工试读少量真实样稿再自动化。
- 不同语言、移动端、键盘、加载/空/错误状态单独验收；修正弱对比度、过长行宽、选择状态和作用范围提示。
- 用连续多期的真实内容检查来源、语种、完整性、重复率与维护成本，不以一次成功生成作为稳定运行的证明。
